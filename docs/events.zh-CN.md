# 事件驱动处理

[English](events.md) | [简体中文](events.zh-CN.md)

0.6.0 使用 Linux inotify 和 root 私有 SQLite 队列，替代反复全量扫描。这是标准 Linux 文件系统事件接口，**不是**有公开文档的 Synology Photos“上传完成”回调。在已审阅文档及 API 描述中未找到受支持的公开 Photos 回调；项目不注册内部 DSM media-index 插件，也不修改群晖索引服务。

## 日常流程

1. 独立收集进程监听 Photos 本地目录的关闭写入、文件移入、新目录树等事件。不跟随目录符号链接，忽略 `@eaDir`、`#recycle` 等隐藏或生成目录。
2. 合并并持久保存事件。协调进程等待源文件指纹稳定，按名称定位 Photos 目录，仅查询该目录，直到出现文件名和大小匹配的索引项。
3. 按用户空间、项目 ID 和阶段持久保存任务。缺失预览优先于兼容视频；保持兼容原视频跳过逻辑。已经开始的视频任务不中断，但独立监听进程继续记录新事件。
4. 失败素材延迟重试；文件变化会使排队任务的身份/缓存标记失效。没有就绪任务时，协调进程等待管道唤醒，收集进程等待 inotify；不定时全量扫描相册。

首次启动及重启补查历史或停机期间的变化。之后只在显式请求、内核事件溢出或根目录监听丢失后恢复时补查；持久队列中的任务跨重启保留。目录尚未完成索引时，只定向重试该目录，不全库重扫。本地账号/根目录发现及进程健康检查仍会定期唤醒，但不会枚举 Photos 相册。

可不重启服务，手动请求一次补查：

```sh
sudo /bin/python3 -I /volume1/@PhotosAssistantNAS/app/service_entry.py reconcile
```

如安装在其他卷，请调整路径。协调进程在下一个调度边界接收请求。这只是补查任务，不强制 Photos 重建索引，也不覆盖已接收资源。

## 异常与边界

监听器就绪后才开始历史补查；注册监听期间目录中新建的近期文件会保留为事件。新建及移入目录会递归添加监听；内核事件溢出会请求重新补查。监听容量或权限不足时停止监听进程并报错，不静默假定覆盖完整；查看私有 `state/events.log`。项目不自动修改系统 inotify 限制。

文件变化事件不代表 Photos 已入库。项目等待匹配的索引元数据，保留 Photos 格式/状态判断及只读源文件校验。此次不增加网络文件系统、未知 Photos 版本、任意符号链接相册的支持。不拦截浏览器上传，不开放 HTTP 服务，不需要账号凭据。

卸载会停止监听，并删除本项目的队列、数据库及事件日志。原文件和 Photos 已接收资源保持原有保留策略。

## 验证

单元测试覆盖队列跨重启保留、预览优先、身份/重试失效、写入稳定、符号链接越界拒绝、定向目录查询、素材删除、溢出补查请求，以及连续任务之间不全量重扫。NAS 测试捕获文件移入和整个目录移入，排除生成缓存事件，重新打开队列后事件仍存在；空闲 3 秒采样中监听进程 CPU 计时没有增长。并不据此保证所有文件系统或上传客户端均兼容。

参考：[Linux inotify 手册](https://man7.org/linux/man-pages/man7/inotify.7.html)。
